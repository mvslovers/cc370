# libc370 corpus gate — differential (#48)

Assembles every non-wip `libc370` module **twice** — once with the `as370` in the
working tree, once with an `as370` built from a baseline revision — and reports
which object decks moved.

```sh
make test-corpus                         # against origin/main
sh as370/tests/corpus/check.sh           # same, directly
BASE=<rev> sh .../check.sh               # against any revision
LIBC370=/path sh .../check.sh            # libc370 checkout (default ../../libc370)
```

Needs the `libc370` checkout beside this repo. Roughly 8 seconds for 743 modules
on an ordinary laptop, plus one compile of the baseline assembler; when the
`as370` sources are unchanged against the baseline it says so and exits at once.

## What it answers — and what it does not

A **regression** guard: *did my change move the corpus, and which modules did it
move.* It is not an **oracle** guard — it cannot tell you as370 was already
wrong, because both sides are as370. That is #23-full, which wants committed
IFOX00 reference decks for the corpus the way `tests/ref/` has them for nine
modules.

The suites that do carry oracles are `tests/run.sh` — nine IFOX00 reference
decks, three of them real generated COBOL, one 113 cards long — and
`tests/listref`, four IFOX00 SYSPRINT listings. Those answer "is as370 right".
This one answers "did as370 change".

## Why it is differential, and not a manifest

Until #48 this compared deck SHA256s against a committed manifest. The manifest
decayed until it could no longer tell a regression from an intended change: 74
modules reported CHANGED in August (#44), 114 by the end of the month, with
nobody having touched as370 in between.

The repair both #44 and #48 proposed was to pin the libc370 commit the manifest
belonged to. **That cannot work.** 710 of the manifest's 737 entries were under
`src/`, and

```
$ git -C libc370 ls-files 'src/**/*.s' | wc -l
0
```

They are `sdk/mklibc.py` output — which `mklibc.py clean` deletes again —
generated by whichever `cc370` happened to be on PATH at the time. So the
baseline depended on three moving inputs: as370, libc370's C sources, and the
other half of this toolchain. Only the first is what the gate is about, and one
of the other two exists in no repository at all.

Comparing two as370 binaries over one tree cancels all three. The corpus is
whatever is on disk, identically on both sides. Nothing decays, nothing needs
regenerating, and there is no "coverage drift" to detect — both sides walk the
same list by construction, which is why the module count went from 737 to 743
without anyone adding anything.

## Reading the result

```
corpus: 743 modules, baseline origin/main
corpus: no module moved -- the working tree's as370 reproduces origin/main deck for deck
```

Anything else names the modules:

```
corpus: asm/@@crt0.asm MOVED
corpus: src/clib/@@stow.s NO LONGER ASSEMBLES (rc 8)
corpus: src/jes/jesprb.s NOW ASSEMBLES (did not under origin/main)
```

A module that assembles on neither side is skipped in silence — that is
pre-existing, not this change's doing.

**It exits non-zero whenever anything moved, including when the move is
intended.** A deck that moves is a decision: say in the PR which modules moved
and why, the way an output-changing change has always had to. `NOW ASSEMBLES` is
reported but does not fail the run — it can only be an improvement.

## Why it is still not in CI

The gate is no longer the obstacle — since #48 it is differential and green. The
corpus is. A fresh `libc370` clone, which is what CI has, carries **27** modules:

```
$ git -C libc370 ls-files | grep -E '\.(asm|s)$' | grep -v /wip/ | wc -l
27          # all of them asm/*.asm
```

The other 716 are generated, so covering them in CI means building `cc370` there
(`make compiler`, the slow path) and running `sdk/mklibc.py` first. Wiring in the
27 alone is cheap and would still guard the hardest hand-written macro paths —
`@@crt0`, `@@crt1`, `@@crtm`, `@@getm`, `@@freem` — and needs `fetch-depth: 0` on
the checkout so the baseline revision is present. That is a decision, not a
detail, so it is left to #48.

## Verifying the gate itself

A guard that cannot fail is worse than none. To confirm it still detects
movement, perturb something every deck carries — the END-record IDR version in
`AS370_IDR_VER`, say — rebuild, and run it: all 743 modules must be reported. It
was checked that way when it was written.
