=head1 NAME

as370 - host-native MVS assembler (IBM Assembler-XF / IFOX00 clone)

=head1 SYNOPSIS

B<as370> [I<options>] I<file>

=head1 DESCRIPTION

B<as370> assembles System/370 HLASM source into an OS/360 object deck (80-byte
EBCDIC ESD/TXT/RLD/END card images) on the host. It is a single-file
reimplementation of IBM's Assembler-XF (B<IFOX00>): macro preprocessor, two-pass
core and object writer, producing decks B<byte-identical to IFOX00> over the
mvslovers ecosystem corpus.

It is invoked automatically by L<cc370(1)> to assemble the compiler's output, and
can also be run standalone on hand-written F<.s>/F<.asm> source.

=head1 OPTIONS

=over 4

=item B<-o> I<objfile>

Write the object deck to I<objfile> (binary).

=item B<-I> I<dir>

Add a macro-library directory to the search list (repeatable).

A member is looked for in each directory in turn, and within a directory under
the name B<as written> first and then lowercased, each with the extensions
F<.macro>, F<.copy>, F<.mac>, F<.asm> and none. An MVS member name is uppercase,
so the name as written is the primary spelling; the lowercase attempt remains
for directories made by hand. Both spellings are tried in one directory before
the next is consulted, so the search order between directories is unaffected.

=item B<-a>[I<sub-options>]

Produce a listing. Sub-options include B<e> (external symbol dictionary) and
B<r> (relocation dictionary); B<=>I<FILE> writes the listing to I<FILE> (must be
the last sub-option). Other sub-options (g/i/m/s/x) are accepted but not yet
produced.

=item B<--sym=>I<FILE>

Write the assembly's symbol table to I<FILE> as tab-separated data, one record
per symbol: name, value, length, type, section, section name, whether the
section is a DSECT, ESDID, whether the symbol is defined, and whether it is an
ENTRY. B<-> writes to standard output. The file carries its own C<#columns>
header, and a destination that cannot be opened is an error of the invocation
(exit 16), never a silent fall back to standard output.

B<One record per symbol, which is one record per NAME.> Where a name is defined
twice the table carries the definition that won and no trace of the other -- see
L</DUPLICATE SYMBOLS>.

This is data, not the listing: the C<s> and C<x> sub-options of B<-a> remain the
human cross-reference pages that B<IFOX00> prints, and still produce nothing.
Values are decimal, and are section-relative for a symbol in a DSECT and
absolute for any other defined symbol. A displacement such as C<8(4,13)> under
C<USING TCB,13> is resolved by taking the nearest value at or below 8 among the
records of TCB's section whose C<defined> is 1 and whose type is not C<ABS>. An
absolute EQU keeps the section its card was written in while holding no address
in it --- every module writes C<R0 EQU 0> through C<R15 EQU 15> inside a CSECT,
and a scan that keeps them answers C<R4> for C<4(,12)>. Where C<defined> is 0 the
symbol was referenced and never defined, and its value says nothing.

=item B<--stmts=>I<FILE>

One record per generated statement, tab-separated, in the shape of B<--sym>:
C<sect sectname secorg org cards loc len stmt gen mdepth mcall_stmt mcall_name
reserves text>. C<-> writes to standard output. cc370#411; the export B<dasm370>'s repair contract
needs and no listing can replace.

B<C<reserves> is the field this exists for.> It says whether a statement
B<occupies> its bytes (C<DC>, C<DS CL1>, an instruction) or only B<aligns> or
B<moves over> them (C<DS 0F>, C<CNOP>, C<ORG>). An object cannot tell those apart
--- both are bytes no TXT card covers --- and two defensible object-side rules
were measured to disagree B<1 % against 14 %> about the size of that population.
Only the source knows, and only at assembly time. Where C<len> is 0 there are no
bytes and the column is vacuous.

C<ORG> is in that list by measurement and it was not there at first. An C<ORG>
that skips forward has a positive C<len>, so it B<claimed> the bytes it moved
over: 18,485 such records, B<602,740 bytes in 2,295 of the 5,528 corpus modules>.
A repair told the C<ORG> card occupies them edits the C<ORG>.

B<C<len> is the location counter ADVANCE, not the bytes emitted.> It includes any
alignment the statement forced, so a C<BR 14> at an odd offset has C<len> 3 and
its first byte is the pad --- which is what the listing shows, the pad at the
statement's own C<LOC> and the halfword after it. The statement's bytes are
C<[loc, loc+len)>.

B<And C<len> is negative where the counter moves back>, because an C<ORG> is a
statement like any other and its advance is its own: 59,443 records in 3,758 of
the 5,528 modules. So B<C<loc> is not a key and an offset is not a function> ---
B<5.97 %> of claimed bytes are claimed by more than one statement, in 3,559
modules. The deck holds what the B<last claimant in listing order> wrote.

B<C<org> and C<cards> locate the card; C<stmt> does not.> A continued statement
occupies several input cards and carries one statement number, so the two
counters diverge and never converge. Measured over 30 modules' real sources,
61,252 open-code cards: C<stmt> locates the card in B<0.8 %> of them and C<org>
in B<99.9 %>. C<cards> is how many input lines the statement spans, so the range
is C<org> to C<org + cards - 1>.

B<C<loc> is module-absolute and C<secorg> makes it usable.> The location counter
does not restart per section, so section 2 of a two-section module does not begin
at 0 --- and an object deck carries B<section-relative> offsets. The
section-relative offset is C<loc - secorg>. It is a column rather than an
inference because taking the smallest C<loc> in a section is wrong the moment a
section is opened, left and resumed. Without C<sect> the counter is ambiguous
outright: measured over the 5,538 module sources, only B<49.7 %> declare a single
section, 23.3 % declare three and 19.7 % four or more.

B<C<mcall_stmt> and C<mcall_name> name the CALL, not merely a depth.> A listing
marks a generated line C<+> and never says which call produced it, leaving a
consumer to walk backwards to the nearest unmarked line and hope. For a
macro-generated card C<org> is the B<call site> --- the card a repair edits ---
while C<text> is the model card with substitutions applied, which is not a card
in the caller's file at all.

C<mcall_stmt> B<has no record of its own>: a call card generates no statement, so
it is not exported. At C<mdepth> 1 its file line is the record's C<org>. At
C<mdepth> 2 and above C<mcall_name> is the B<innermost> macro, whose call card is
a model card in a library and in no file the caller can edit, while C<org> still
names the B<outermost> open-code call, which is one. B<20.3 %> of generated
records are at C<mdepth> 2 or deeper.

B<The consumer must check C<org>, and the test is a prefix test.> A statement
from a C<COPY>'d member keeps the C<COPY> statement's origin and carries nothing
that marks it --- C<gen> 0, C<mdepth> 0, C<mcall_stmt> and C<mcall_name> empty,
exactly like open code --- so C<org> names the C<COPY> card and only comparing
C<text> against the statement at C<org> says so. Measured over 490 COPY-derived
records: the card at C<org> is a C<COPY> card B<490 of 490>, C<text> is not a
prefix of it B<490 of 490>, and C<org> is B<never> a line inside the member. The
false-positive control over 47,534 open-code records gives B<0> with the prefix
test and B<5> with equality, so it is prefix and not equality.

=item B<-v>

Print the assembler version.

=item B<--help>

Show usage and exit.

=back

=head1 DUPLICATE SYMBOLS

A symbol defined twice is accepted, the later definition wins, and B<nothing is
said> -- no diagnostic, no change to the return code. This is B<not> an
oversight: it is what Assembler XF does, measured rather than assumed.

Two real modules of the MVSBLD corpus were run through IFOX00 on the pinned
oracle in September 2026, one of each shape:

=over 4

=item *

C<IFCRDESM> -- a B<conflicting> pair: C<IPLTIME DS XL4> inside one section and
C<IPLTIME EQU IPLHEAD+12> in another, two sections and two values.

=item *

C<AMDSAUCB> -- a B<same-value> pair: C<CVT EQU 0> and, 1730 cards later,
C<CVT EQU CVTMAP> where C<CVTMAP> is also 0.

=back

IFOX00 answered C<NO STATEMENTS FLAGGED IN THIS ASSEMBLY>, C<HIGHEST SEVERITY
WAS 0>, for both. C<as370> gives rc 0 and no diagnostics for both. So the
silence is a B<fidelity match> and not a gap, and adding a diagnostic here would
make C<as370> diverge from its reference.

B<What follows from it is a working hazard rather than a defect.> The losing
definition is recoverable from no C<as370> output at all: the object carries the
winner's value, the listing shows the statement as written, and C<--sym> holds
one record for the name. A field added to a DSECT that collides with a register
equate defined elsewhere in the same assembly therefore keeps its bytes and
loses its name, and the module still assembles clean. When editing a large
source against a fixed object -- bringing an old level up to a shipped one, say --
that is a mistake nothing in the toolchain will report, and the cheapest guard
is to choose names that cannot collide rather than to look for a warning that
neither assembler will give.

=head1 MACRO SEARCH ORDER

Highest priority first:

=over 4

=item 1.

The B<-I> directories.

=item 2.

C<$AS370_MACLIB> --- a colon-separated override.

=item 3.

A built-in relocatable default F<< <exedir>/../macros >>. For an installed
as370 (in F<I<prefix>/bin>) this resolves to F<I<prefix>/macros>, the macro
library installed by B<libc370>, so as370 assembles with no B<-I> and no
environment.

=back

=head1 EXIT STATUS

Follows IFOX C<JERMSGCD>: B<0> clean, B<4> warning, B<8> error, B<12> severe,
B<16> terminal. Silent on success.
