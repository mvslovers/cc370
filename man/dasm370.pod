=head1 NAME

dasm370 - disassemble a control section of an OS/360 object deck

=head1 SYNOPSIS

B<dasm370> [I<options>] I<deck.obj>

B<dasm370> B<--align-diff> I<reference> I<candidate> [I<options>]

=head1 DESCRIPTION

B<dasm370> turns one control section of an object deck back into assembler
source that L<as370(1)> can assemble again. It is the first stage of the source
recovery the B<mvs38src> project needs: a CSECT for which an object exists and
no source is not repairable, and disassembly is the only route to a module that
can be built.

B<The decoder is as370's own opcode table, inverted.> It includes
F<as370/include/opc_table.h> rather than carrying a copy, so the disassembler
agrees with the assembler by construction --- which is the property the round
trip below depends on. A decoder built from a second copy of that data drifts
silently: it still assembles, still compares, and disagrees about an instruction
neither tool reports on.

B<Nothing is emitted that does not reproduce its own bytes.> Every instruction is
decoded, re-encoded from the decoded fields and compared against the bytes it
came from; anything that does not reproduce itself is written as C<DC X'..'>.
Re-encoding is necessary and not sufficient --- an operand also has to be one the
assembler will accept --- so a decimal rounding digit above 9 or an instruction
at an odd offset is data too.

B<The RLD decides what is data before the decoder runs.> A field a relocation
dictionary entry names is an address constant and is never decoded as an
instruction. That is the one place an object-deck disassembler has ground truth,
and asking it afterwards would be too late: a decoder that decodes first and
relocates after has already produced a plausible instruction for every address
constant in the module, and neither the bytes nor the round trip will object.

=head1 OPTIONS

=over 4

=item B<--csect> I<NAME>

Disassemble this control section. The default is the first one in the deck.
An unknown name is an error (exit 2), not an empty result.

=item B<--align-diff> I<reference> I<candidate>

Disassemble B<both> objects of one control section and align them statement by
statement, so that a displacement which moved because something before it changed
length is reported as a B<consequence> rather than as a change of its own. Writes
a report, not a disassembly; reads no hint file. See L</ALIGN-DIFF> below.

=item B<--labels> I<displacement>|I<sequential>

How a generated label is named. C<displacement> (the default, unchanged) names it
after the offset it sits at --- C<L0000A4> for C<X'A4'>. C<sequential> numbers
them instead, C<L0010>, C<L0020>, in offset order.

B<A displacement-derived name is wrong the moment a statement is inserted above
it>, and it still assembles: the label reads C<L0000A4> and now sits at
C<X'A6'>. No diagnostic, no moved byte --- so the round trip, L<cmplmd370(1)> and
every comparison this project has report success on it. Inserting statements is
the repair workflow, not a hypothesis, so use C<sequential> for any disassembly
that will be edited or deposited. cc370#396.

The names change and the object does not: a section disassembled either way
reassembles to the same bytes.

=item B<--reach-report>[=I<SET>]

The #383 reachability traversal's coverage, as data and without a disassembly.
Traverses from the B<code roots> --- the C<SD> (the section origin), the C<LD>/C<LR>
entries this section owns, the C<END> entry B<on a deck only>, and a table of
address constants a branched-through register was loaded from --- and reports what
it reached. I<SET> is C<none|r15|balr|rld|lr|both|bothlr|acon|all> (default
C<all>) and selects which base assumptions are allowed, so each one's
contribution can be measured on its own --- and measured they are worth about
B<5 % and 7 % alone against 77 % together>, five times their sum, because C<R15>
carries the branch over an eyecatcher into the prologue and the prologue base
carries the body. See L</REACHABILITY> below.

B<The applied form is not implemented, and that is a measurement.> C<--reach>
exits 16 and says so.

=item B<--derive-hints> I<SRC>

Assemble I<SRC> with L<as370(1)> and write out what it found, as a hint file: the
labels the source named and the base registers with the lifetimes the assembly
gave them. **A translator, not an analysis** --- it reads as370's C<--sym> and
C<--usings> exports and writes a third file; nothing here is inferred.

It takes B<-I>, and B<records the list in the file it writes>. A hint set derived
against the wrong macro library is a wrong hint set that looks entirely right, so
the file announces which library built it rather than leaving that visible only to
someone who happens to diff two runs.

B<The offsets are the source's.> Applied to a module that has diverged from it,
a label past the first divergence names the wrong bytes --- symbolically,
consistently, and without moving one, so no round trip objects. That is what the
anchors are for.

=item B<--infer>

Candidates from the code itself, for the CSECT that has no source at all. Reads
the module and writes a hint file in which B<every candidate is a comment and
none is applied>.

That is the issue's instruction rather than caution. A base register is not "R12
holds X" but "from here until it is dropped, resolve C<D(12)> against X". The
B<point> is sometimes ground truth; the B<range> never is, because a module has
no C<DROP>s and no block structure to read one from. Get the range wrong and
every displacement inside it resolves against the wrong section --- plausibly,
consistently and falsely, without moving a byte, so neither the round trip nor
anything downstream can object. Promoting a candidate is a human's deliberate
edit, and what the human supplies is the lifetime.

Feeding an inferred file back to B<--hints> therefore changes nothing, which is
asserted.

The B<evidence kind> is recorded separately from any confidence, because only
some of them can be re-judged at all:

=over 4

=item B<prologue>

C<BALR Rn,0> --- the base is the next instruction's offset. Exact about where,
silent about for how long.

=item B<rld>

A register loaded from an address constant whose relocation resolves into this
section, and afterwards used as a base. The RLD is the one place an object-deck
reader has ground truth, so a later reader can re-check this against the object
itself.

=item B<pattern>

A register the code addresses through with no origin found. Re-judgeable against
nothing --- it records a question, not an answer, and says which registers a
reader still has to account for.

=back

B<In practice this is one kind plus two rarities.> Measured over the 772
no-source CSECTs, which are the population this mode exists for and which are
readable only as bound members: 772 ran, B<606 produced candidates>, 5,126 in
all --- 4,690 C<pattern> (91 %), 408 C<prologue> (8 %), B<28> C<rld> (1 %). The
same proportions hold on a 30-CSECT deck sample: 344 / 28 / 2. So the usual output is a
list of registers a reader must still account for, which is the honest and
useful thing for a section with no source --- but it is not three kinds in
balance, and reading the list above without that number would suggest it is.

B<A C<BALR Rn,0> whose register is never used as a base is not claimed as a
prologue.> It is reported, because it happened, as C<pattern> with
C<note=balr-not-used-as-base>.

B<What C<prologue> can and cannot mean: it detects the idiom, not the
declaration.> C<BALR Rn,0> is a run-time fact and
C<USING> is an assembly-time one, and B<an object records the first and cannot
record the second>. Three measured consequences, none of them repairable here.

C<IGG08113> writes C<BALR R15,0> and then C<B 32(,R15)> by hand, with no C<USING>
anywhere. The idiom is present and the addressability is not --- and from the
object B<those are the same bytes>.

C<IECVERPL> establishes R10 a second time at C<X'246'> with no C<USING> beside
it, so the assembly resolved everything against R10 = 0 throughout. The candidate
is a true statement about the code and B<a false one as a hint>: applying it would
resolve displacements against an origin the assembly never used.

A data area holding C<X'0510'> is C<BALR 1,0> to anything reading bytes. Only
reachability (issue #383) can say that nothing branches there; an opcode gate
cannot. The real case is worse than the hex form suggests: C<ICKTR02> carries
C<DC F'01296'>, and B<decimal 1296 is C<X'00000510'> > --- the low half of an
ordinary fullword constant is the idiom, on a card nobody would suspect.
C<dasm370/tests/infer.s> pins both forms deliberately.

The C<R2 == 0> guard is correct and does separate the idiom from a call ---
C<BALR R1,R15> is C<X'051F'> and never reaches it. What it cannot separate is an
instruction from data that looks like one.

=item B<-I> I<DIR>

A macro library for B<--derive-hints>. Repeatable, and order is preserved.

=item B<--as370> I<PATH>

Which B<as370> to run. The default is the one beside this binary --- the install
layout puts them in one directory --- and then whatever C<PATH> finds. In the
build tree they are siblings and neither applies, which is why this exists; the
derived file records what actually resolved rather than what was intended.

=item B<--anchors=>B<refuse>|B<report>

What a failed check does --- B<every> check, not only a failed C<[[verify]]>.
Measured over the 2,292 length-differing CSECTs: of 634 refused applications,
B<404> were a derived base's range overflowing a B<shorter> section --- which is
the population's defining property rather than an error --- and B<158> were the
label collision detector firing, which is a divergence report with both offsets
in it. 562 of 634 were measurements being refused instead of reported. Under
B<report> the base range is clamped and says so, a label or anchor past the end
says the module is shorter, a collision is written with both offsets and the
hint's name is B<dropped>, and the run continues. B<refuse>, the default, stops at the first one
and writes nothing --- right for a hand-written hint file, where a failed
assertion is a mistake. B<report> disassembles anyway and writes each failure as
a comment at its offset.

B<A derived file's anchors exist to find the divergence, not to guard against
it.> Measured over 909 length-differing modules: a median of 9 divergence points
per module, the first at median offset C<X'14'> and at 2.1 % of the section, with
65 % diverging inside the first tenth. So an anchor at a base register's
establishing point --- typically offset 2, after a C<BALR> --- checks the one
place that never moves, passes, and leaves every later label wrong; and an anchor
per label block would refuse essentially everything. Anchors are therefore
written densely, and what is worth having is neither a pass nor a refusal but a
B<location>: the first failure bounds where the module and the source part
company. Across a set of modules that is a table of offsets; a refusal would give
one bit each.

=item B<--hints> I<FILE>

Read a hint file: labels, data and fill runs, base registers with a lifetime,
and the C<VERIFY>/C<REPLACE> pair. L</HINTS> has the grammar in full. Anything outside
that grammar is B<refused>, with the line number, and nothing is written ---
a hint silently ignored is a file that looks applied and is not.

=item B<--format> B<card>|B<free>

B<card>, the default, writes 80-column records with the sequence number in
columns 73-80 and column 72 left blank, so the result drops straight into a
fixed-format source library. B<free> writes the same statements without the
padding, for reading.

=item B<--isa> B<app>|B<s370>|B<s360>|B<full>

Accepted; only B<full> is implemented, and any other value prints a note and
behaves as B<full>. Problem-state against privileged is a per-mnemonic attribute
F<opc_table.h> does not carry, and inventing it here would be the second copy the
shared table exists to prevent.

=item B<-o> I<FILE>

Write to I<FILE> instead of standard output.

=item B<-v>, B<--help>

Print the version, or the usage.

=back

=head1 WHAT IT RECOVERS

Instructions in every format as370 encodes; extended branch mnemonics from the
implied mask, in the spelling IBM's own source uses more often; address constants
from the RLD, as C<A(...)> and C<V(...)> --- or the length-modified forms where
the field is not fullword-aligned, which is ordinary and moves every statement
after it if written as C<A(...)>; C<ENTRY> statements from the deck's LD entries,
which no comparison of section text can see; C<EXTRN> for everything the
relocations point at that is not this section; and runs no TXT card covers as
C<DS>, because a hole is not a zero.

=head1 HINTS

A hint file says what the bytes cannot. It is a subset of TOML, parsed in
B<dasm370> itself with no dependency, and the grammar is deliberately small so
that everything outside it can be refused rather than skipped:

    # comment                to end of line; a blank line is ignored
    key = value              at the ROOT, before any table header
    [[table]]                begins one element of an array of tables
    key = value              belonging to it

A value is C<"a string"> or an integer, decimal or C<0x>-prefixed. A
single-bracket C<[table]> is refused, so there is one way to write a table. An
unknown table, an unknown key, a key given twice, a missing required key, a value
of the wrong kind and an offset outside the section are each exit 16 naming the
line --- and each leaves no output file, because the output is opened after every
refusal.

=over 4

=item B<isa> = I<"s370">, B<prefix> = I<"P">  (at the root)

As B<--isa>; the command line wins over the file. B<prefix> replaces the C<L> of
a manufactured label such as C<L0000A4>, so two disassemblies can be assembled
together. One or two characters: the name is the prefix plus six hex digits and a
symbol holds eight.

=item [[label]] B<at>, B<name>

What the source called this offset. It outranks the C<ENTRY> name the module
carries, which in turn outranks the manufactured one. A label inside an
instruction re-cuts it --- that instruction becomes C<DC> --- which is right:
something enters there, so the boundary was wrong.

=item [[data]] B<at>, B<len>

Do not decode this run as instructions.

=item [[fill]] B<at>, B<len>

One repeated byte, written with a duplication factor: C<DC 184X'00'> instead of
twelve cards of hex. Refused unless the run is covered by a TXT card, uniform,
free of relocations and free of labels --- each of which is arithmetic, because a
fill that is wrong moves bytes.

=item [[base]] B<reg>, B<value>, B<from> [, B<to>]

A base register covering a range of B<this section> --- ordinary addressing,
"where am I in my own CSECT". C<value> is what the register points at: a symbol
(the section, an C<ENTRY> of it, or a C<[[label]]> in this file) or an offset.

B<from> and B<to> are the lifetime, and B<there is no form without one>: a base
register is not "R12 holds X" but "from here until it is dropped, resolve
C<D(12)> against X". B<to> may be left out because there is a right default and
it is not a guess --- one base register addresses 4096 bytes, so an omitted C<to>
is C<from> + 4096, clamped to the section. An omitted C<to> is computed and an
explicit one is asserted, so only an explicit one is refused for running off the
end.

A hint base is B<applied>, because its writer supplied the lifetime. It emits
C<USING> and C<DROP> at those offsets, resolves C<D(B)> to a symbol within them,
and labels the C<BC> targets it makes readable --- C<BC> alone, because that
format is definitionally a branch, where an C<RX> instruction's second operand is
data as often as it is a target.

A symbol is written B<only where as370 would choose the register the bytes name>.
The assembler's rule is the smallest displacement still in range and, on a tie,
the higher register; where a second base would win, the numeric form stays. Two
live bases on one register are refused, because as370 holds one entry per
register and cannot be in that state.

=item [[verify]] B<at>, B<bytes> | B<date>

Assert the text. C<bytes> is hex; C<date> is C<"mdy"> for the C<mm/dd/yy> shape
C<&SYSDATE> writes or C<"julian"> for the C<yy.ddd> one an eyecatcher carries.
Both exist because one shape alone is noisy over the corpus.

=item [[replace]] B<at>, B<bytes>

Patch the text before disassembly --- the date and serial class. B<Every
C<REPLACE> must be covered by a C<VERIFY>>, and the C<VERIFY> reads the original
bytes: a patch applied to bytes nobody asserted is a patch applied to whatever
the module happens to hold.

=back

B<A derived label that disagrees with the module's own name refuses, naming both
offsets.> An C<ENTRY> in the ESD is the module's statement about where something
B<is>; a derived C<[[label]]> is our source's statement about where it B<was>.
One symbol at two offsets means the module has diverged, and reporting it beats
emitting both names and letting as370 report a duplicate symbol far from the
cause. It fires on 18 % of the length-differing population --- 409 of 2,292 carry
named offsets at all --- so it complements the anchors rather than replacing
them, but where it fires it is the better instrument, because the name is the
module's own.

C<[[using]]> and C<[[dsect]]> parse and refuse as not implemented. They are one
thing, and C<[[base]]> is a different one: a C<USING> points a register at a
B<DSECT> and carries that mapping, where a base covers the section itself.
Resolving into a dummy section needs a symbol table, which C<--derive-hints>
brings. C<base> written at the root refuses too, naming the table --- it is a
table here, not a scalar.

The split, the lifetime and the C<from> + 4096 default are as Pospischil's
B<mvs38dasm> documents its own control statements. That tree carries no licence
statement, so it is read for what a word means and never copied: the semantics
are its, the file format is ours.

=head1 ALIGN-DIFF

Two objects of the same control section at different maintenance levels, both
disassembled, aligned, and every difference classified: an insertion, a deletion,
a changed data run, a B<constant change>, or a B<displacement shift> that is a
consequence of one of the others.

=head2 The key is the statement with its displacements masked

Everything rests on this. A statement's identity has to survive a shift, or every
statement after an insertion reads as a change of its own and a pair differing by
one insertion reports six differences instead of one.

The key is built from the B<bytes>, with the displacement fields cleared and the
base-register nibbles kept --- a different base register is a different statement.
It is not built from the text B<dasm370> prints: our own output embeds an offset
in a manufactured label, C<A(L000410)>, so a shifted internal address constant
would change its own key. An address constant's key names its target and its
width and never its value, because an external one's text is an addend in a deck
and a binder-resolved address in a bound member --- two different quantities,
which is why the value is masked on both sides rather than compared across.

=head2 A shift is measured, never assumed from position

#112 states the assumption this mode exists to convert as I<"the displacement
shifts following an attributed length change are consequences">. That is not the
rule. In the first constructed case the shift is at C<000002> and the insertion
at C<00000A>: the instruction addresses data at the end of the section, and
inserting anywhere before that data moves it. B<A shift can precede its own
cause>, so position relative to a change is not evidence and is not used.

What a displacement delta is compared against is the B<cumulative shift
function>, computed from the alignment itself: for a matched pair,
C<shift = cand.at - ref.at>. A delta is a consequence exactly when it is a value
that function takes.

Two boundaries matter and both were found by a case rather than by reasoning.
The first is that the function must count B<every> statement, code and data
alike: two insertions of 2 and 4 bytes move every displacement by B<8>, the
missing 2 being alignment padding the assembler added when the first insertion
pushed the data area off its fullword boundary. A prefix sum over the detected
code insertions gives 6, and every displacement in the module is then reported as
a constant change --- a whole module of findings where there are none. The second
is that B<the end of the section is an alignment point too>: in that same case
the padding sits inside the trailing data run, which does not match, so no
matched pair carries C<+8> at all.

=head2 What the report says, and how strong it is

Each finding and each consequence is one line at its own offset, and the last
line is a C<SUMMARY> a population run can grep. It carries its own denominators
--- C<refstmt=>, C<candstmt=>, C<reflen=>, C<candlen=> --- because a finding
count over a population cannot be normalised without a size, and C<first=>, the
offset of the first finding, which is the scalar a triage run ranks on. A module
with no finding reports C<first=->, never C<first=000000>. Two things are printed on every
module because they decide what the classification is worth:

=over 4

=item the B<size of the shift set>

which is the strength of the membership test. Over the 832-module target
population the median is 16 values and the maximum 317 --- of 8,191 possible
deltas, 0.2 % and 3.9 %. Membership in a 317-value set is close to no test at
all, and only the printed size tells a reader which modules the verdict means
something for.

=item which B<shift(B)> case the module is in

The exact rule is C<delta == shift(T) - shift(B)>, and without a C<USING> the
disassembly has no B. Where the base is established before every change
C<shift(B)> is 0 and the test is exact; where a change precedes the prologue the
base moves too and the test is weaker. The report says C<base=exact>, C<base=weak> or
C<base=none> per module rather than assuming the common case. The third is not a
refinement of the second: a module that writes no C<BALR Rn,0> at all has no base
to shift, and most of #112's corpus is PL/S, which largely does not write one.
Over the 832-module target population: 158 exact, 347 weak, 327 none.

=back

No byte count is reported that is not attached to a named statement or run. A
deck's text and a bound member never agree on relocated address constants, so a
byte count over a member/deck pair means one thing under an alignment and another
under L<cmplmd370(1)>, which clears the RLD-covered bytes.

=head2 What it does not do

It reads no hint file and writes no disassembly, and B<--hints>, B<--infer> and
B<--derive-hints> are refused alongside it rather than combined. A hint file
supplies exactly the base this mode says it does not have; that is a real
refinement and a later one, and combining them now would mean reporting two
different C<shift(B)> cases from one run without saying which applied where.

An uncovered byte is read as zero, on both sides. A deck says which bytes no TXT
card covered and a bound member cannot, because the binder filled them before it
wrote the member --- so against a member every such hole is a difference that
belongs to the transport. Filling to zero reads the deck as the member form of
itself; a member whose hole is B<not> zero still differs and still says so.

An alignment needing more than 20,000 insertions and deletions is B<abandoned>
rather than approximated, and the report says so. An alignment that had to guess
would produce findings indistinguishable from the real ones.

=head1 REACHABILITY

=head2 What a code root is, and what it is not

B<An RLD target is a LABEL root and never a code root.> An address constant says
where something points, which is data at least as often as code; treating a
C<DC A(BUFFER)> table as code reintroduces exactly what reachability exists to
remove. The same word becomes a B<code> root when a register loaded from it is
B<branched through> --- and the discriminator is the C<BR>, not the adcon. That is
why a base derived from an address constant reaches nothing on its own: I<it has
the targets and lacks the gate.>

The index is never resolved and does not need to be. What is recognised is that
the load's target region is relocated; every relocated word of that table is then
a root. The run is taken from the load's target B<or from the word immediately
after it>, because index 0 is a null slot holding zero, and a zero address
carries no relocation --- a rule anchored strictly on the target promotes nothing
on the modules it was derived from.

B<The C<END> entry is a deck root only.> Two C<ld370> links differing in nothing
but the entry point produce byte-identical members; the entry lives in the PDS
directory, which an extracted member does not carry.

=head2 Bases are discovered by the walk

Only C<R15> is seeded --- it holds the entry point by MVS linkage convention, which
is what a branch over an eyecatcher at offset 0 relies on. Everything else is
found by walking: a C<BALR Rn,0> the traversal arrives at, and a base copied by
C<LR>. B<A pre-scan reads a section's data as well as its code> and adopts
halfwords that decode as prologues but are constants. I<The difference between a
prologue base and a phantom is not a property of the bytes --- it is whether the
traversal arrives at them.>

=head2 Why the applied form is not shipped

B<Which denominator, because FOUR are in circulation and they disagree.> The
C<reached=> and C<dark=> fields of the report are byte counts over the B<whole
section>, data included, and they are exact. Every percentage quoted below and in
cc370#383 is a different quantity, and it is the one least obvious from the
name: B<the reached set INTERSECTED with the witness, over the witness> --- of
the bytes a real source listing calls code, the fraction the traversal reached.
Over the 30 control sections, one run, C<--reach-report=both>:

    reached / section length                        62.1 %
    reached / the witness's code bytes (62,078)     80.0 %
    reached / dasm370's own code classification     75.4 %
    (reached AND witness) / witness                 76.6 %   <- what is quoted

B<A reader who divides the report's own byte counts by a code total gets 80.0 and
will conclude this page is wrong.> They are not; they computed a different thing.
Note also that the third and fourth rows agree to within 1.2 points for entirely
unrelated reasons --- one narrows the numerator, the other widens the denominator
by 3,810 bytes --- so B<numerical agreement between two figures is not evidence
that they measure the same quantity>, and that near-coincidence was measured here
rather than assumed away.

The report publishes no percentage at all for the same reason:
C<reached / sect_len> punishes a section for being half table, so the tool states
what it counted and the reader states what they divided by. B<A coverage number
whose denominator is unstated is not a coverage number.>

Measured over 30 control sections whose real source says which bytes are code:
the traversal reaches an aggregate of B<82.2 %> and a B<median of 97.7 %> by that
definition, and the distribution is bimodal --- 25 of the 30 essentially
complete, five near zero.
Applied, it darkens B<12,558 bytes the source calls code> against B<2,300 bytes
of genuine table> it correctly silences, and recovers 130 bytes of code that
previously did not decode. The best threshold on its own coverage is
break-even.

B<Byte-safe is not harmless.> A module whose real code becomes C<DC> reassembles
byte-identically, so the round trip and every gate built on it report success.
The limit is the B<base map> and not the root set: one module has four roots and
reaches 1.1 %. cc370#383 carries the ledger.

=head1 WHAT IT DOES NOT

B<It infers nothing.> Without a hint file no C<USING> is reconstructed and no
branch target is labelled, and an inferred C<USING> --- when one exists --- will
be written to the hint file and never applied. The reason is not timidity: get a
base register's lifetime wrong and every displacement in the wrong range resolves
against the wrong section, producing symbols that are plausible, consistent and
false while the bytes stay exactly where they were, so neither the round trip nor
anything downstream of it can object.

Only one section is written per run, so a deck holding several needs one run
each, and the result reassembles the section rather than the deck.

=head1 THE ROUND TRIP, AND WHAT IT CANNOT SEE

C<dasm370 -E<gt> as370 -E<gt> cmplmd370> is the acceptance gate: run it over a
corpus and the disassembler is either right or it is not.

It has one blind spot and it is worth stating, because it is where a
disassembler's errors hide. B<A byte decoded as the wrong instruction that
re-encodes to the same bytes passes it.> Swapping which of two spellings of one
encoding is printed --- C<BE> for C<BZ> --- changes every listing and no byte.
So exit 0 proves fidelity to the member and not correctness of the reading, and
the suite asserts the mnemonics separately.

Most of what B<--hints> adds is a rule rather than a behaviour, and a rule cannot
be shown by a fixture that passes. Each is therefore scored against a mutant of
the current source, with the scores recorded in F<dasm370/tests/run.sh>.

=head1 EXIT STATUS

B<0> a section was written, or B<--align-diff> compared two, B<2> no such
section, B<4> B<--align-diff> abandoned the alignment, B<16> the invocation or
the input is wrong.
